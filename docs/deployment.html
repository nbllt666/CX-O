显存分配策略（单卡 20GB 场景）

单卡跑全部服务时显存比较紧张。推荐策略：LLM 占 ~18GB（gpu_memory_utilization=0.9），Orpheus TTS 占 ~8-10GB（gpu_memory_utilization=0.45），SNAC 解码器走 CPU 避免争抢。如果显存不够，优先保证 LLM + ASR，TTS 可以用 F5-TTS 或 CosyVoice 替代。

LLM 大语言模型（通过 Ollama 拉取）

🔌 配套服务

CX-O 运行依赖以下外部服务。其中 Ollama 是必须的，Weaviate 和 Neo4j 按功能需求启用。

必须

Ollama — 本地 LLM 推理

CX-O Server 启动时会连接 Ollama 加载对话模型和嵌入模型。不启动 Ollama，后端无法正常工作。

默认地址http://localhost:11434
端口11434
安装方式从 ollama.com 下载安装包
启动命令ollama serve（安装后默认作为服务运行）
配置位置config/default.yaml 第 30-31 行
推荐

Weaviate — 向量数据库

记忆系统的语义搜索依赖向量数据库。支持两种模式：独立服务或嵌入式。

默认端口HTTP 8090 / gRPC 50061
独立服务启动Docker: docker run -p 8090:8090 semitechnologies/weaviate
嵌入式模式配置 vector_backend: weaviate_embedded，无需独立服务，自动嵌入进程
配置位置config/default.yaml 第 100-107 行

注意

虽然 default.yaml 中列出了 Chroma、Milvus Lite、Qdrant 等后端，但后端代码当前仅支持 weaviate 和 weaviate_embedded 两种。配置其他后端不会生效。

可选

Neo4j — 图数据库

知识图谱功能依赖图数据库。如果不使用图谱功能，可以关闭（graph_enabled: false），后端会跳过初始化。

默认端口bolt 7687
启动方式Docker: docker run -p 7687:7687 neo4j
配置位置config/default.yaml 第 110-115 行
关闭方式设置 graph_enabled: false
内置

SQLite — 主业务数据库

主业务数据存储在 SQLite 文件中，无需额外安装服务。包括 data/cxhms.db（主库）、data/memories.db（记忆库）、data/sessions.db（会话库）等。

🚀 启动顺序

服务有依赖关系，必须按正确顺序启动。下面是完整的启动流程。

完整启动流程

  1. 基础环境准备
    # 创建 Python 虚拟环境
cd c:\CX-O
.\create-env.bat
call py311\Scripts\activate.bat

# 前端依赖
cd CX-O-Frontend
npm install
  2. 拉取所有模型
    # Ollama 模型
ollama pull qwen3-vl:8b
ollama pull nomic-embed-text

# 语音模型
python download_voxcpm2.py
python download_voxcpm_support.py
python cosyvoice\download_models.py

# Orpheus（如需使用）
huggingface-cli download canopylabs/orpheus-multilingual-research-release \
  --local-dir ./models/orpheus-multilingual
  3. 启动基础设施服务
    # Ollama（必须最先启动）
ollama serve

# Weaviate（如需向量搜索）
docker run -d -p 8090:8090 -p 50051:50051 semitechnologies/weaviate

# Neo4j（如需知识图谱）
docker run -d -p 7687:7687 neo4j
  4. 启动 Docker 推理服务（可选，按需启动）
    # ASR 语音识别
docker compose up -d asr-sensevoice

# Orpheus TTS
docker compose up -d orpheus-tts

# LLM（如不用 Ollama，用 vLLM 替代）
docker compose up -d llm

# F5-TTS（注意端口冲突，需调整 F5TTS_PORT_HTTP）
F5TTS_PORT_HTTP=8500 docker compose up -d f5-tts-triton
  5. 启动 CX-O 应用服务
    # 语音工作站（如需声音克隆功能）
cd CX-O-VoiceWorkStation
.\start.bat

# 后端服务（核心，必须启动）
cd CX-O-SERVER
.\start.bat

# 前端服务（必须启动）
cd CX-O-Frontend
.\start.bat
  6. 访问应用
    浏览器打开 http://localhost:5173，首次访问会引导确认后端连接。

Orpheus TTS 容器内部架构

Orpheus 使用单容器双进程架构：vLLM 后端和 FastAPI Bridge 在同一个容器里运行。

  1. vLLM 启动：加载 Orpheus 3B 模型到 GPU，监听容器内 8000 端口
  2. 健康检查等待：最多等 120 次（每次 5 秒）等 vLLM 就绪
  3. Bridge 启动：vLLM 就绪后启动 FastAPI Bridge，监听 5060 端口

Bridge 负责把 OpenAI 兼容的 TTS 请求转成 vLLM 推理调用，再用 SNAC 解码器把 token 转成 24kHz PCM 音频。

🎯 双卡部署（ELP-Orpheus）

追求极致低延迟的高级部署方案。需要双卡 Linux 服务器 + FasterTransformer 编译环境。

高级

ELP-Orpheus 双卡架构

ELP-Orpheus 是自研的低延迟推理引擎，通过双卡物理隔离实现 LLM 和 TTS 并行推理，目标首字延迟 <60ms。

组件 GPU 模型 显存占用
LLM FT 引擎 GPU 0 Gemma 4 E4B（FasterTransformer 编译） ~18GB
Orpheus TTS GPU 1 FT Llama-3B 骨干 + Audio Head + SNAC ~8-10GB
SenseVoice ASR CPU 侧 SenseVoice Small —

双卡部署编译依赖

  • FasterTransformer（C++ 编译）
  • PyTorch、Triton (triton-lang)、pyzmq、pybind11
  • CUDA Toolkit (sm_86)、cuBLASLt、nvcc
  • Audio Head C++ 扩展：cd ELP-Orpheus/ft_engine/decoding_cpp/ && python build_audio_head_cpp.py

Windows 限制

ELP-Orpheus 的 FT 引擎需要 Linux 双卡服务器 + FasterTransformer 编译环境。Windows 开发环境会自动回退到 MockFTLlama，不提供真实推理能力。另外，Windows 下 IPC 的 endpoint 需改为 tcp://127.0.0.1:5555（不支持 Unix Domain Socket）。

双卡启动顺序

  1. 启动 Gemma（GPU 0）：FT 引擎加载 Gemma 4 E4B 模型
  2. 启动 Orpheus（GPU 1）：FT Llama-3B + Audio Head + SNAC
  3. 启动 SenseVoice ASR（CPU）：中央调度器

启动顺序不能颠倒

必须先启动 Gemma (GPU 0) 再启动 Orpheus (GPU 1)，否则 Orpheus 会在 ZeroMQ 上空转等待。

❓ 常见问题

部署和运行中常见的问题排查。

后端启动报错连不上 Ollama

确认 Ollama 服务在运行（ollama serve 或检查系统服务）。默认地址 http://localhost:11434。确保 qwen3-vl:8b 和 nomic-embed-text 都已拉取（ollama list 查看）。

语音对话没声音

语音对话依赖 ASR 和 TTS 两个独立服务。默认配置走远程模式（asr.mode=remote + tts.mode=remote），需要：

  • 启动 ASR 服务：Docker docker compose up -d asr-sensevoice（端口 8005）
  • 启动 TTS 服务：根据 tts.engine 配置启动对应服务
  • 检查 config/default.yaml 中的 asr.remote_url 和 tts.remote_url 是否指向正确地址

Orpheus TTS 首次请求很慢

这是冷启动问题。后端启动时会自动发预热请求（非流式 + 流式双重预热），但如果 Orpheus 容器刚启动还没就绪，预热会失败。等待 Orpheus 容器 health check 通过（docker compose ps 查看）后重启后端即可。

显存不足（OOM）

单卡跑全部服务时显存可能不够。解决方案：

  • 降低 LLM 的 gpu_memory_utilization（如 0.9 → 0.7）
  • 降低 Orpheus 的 ORPHEUS_GPU_MEM_UTIL（如 0.45 → 0.2）
  • SNAC 解码器走 CPU（ORPHEUS_SNAC_DEVICE=cpu）
  • 关闭不用的服务（如不直播就关 F5-TTS）
  • 使用嵌入式 Weaviate 替代独立服务节省内存

前端连接不上后端

检查 CX-O-Frontend/.env 中的 VITE_API_URL 是否指向正确的后端地址。默认 http://127.0.0.1:8000。前端启动时会请求 /health 接口检查连通性，连不上会显示引导页。

端口冲突

F5-TTS 默认端口 8000 与 CX-O Server 冲突。在 .env 中设置 F5TTS_PORT_HTTP=8500（或其他空闲端口）来避免冲突。同时更新 config/default.yaml 中 TTS 的 remote_url 指向新端口。

Weaviate 连接失败

两种解决方案：1）启动独立 Weaviate 服务；2）改用嵌入式模式，设置 memory.vector_backend: weaviate_embedded，无需独立服务。如果不需要向量搜索，设置 memory.vector_enabled: false 关闭。

ModelScope 下载慢

下载脚本使用 ModelScope（阿里云），国内网络通常较快。如果仍然慢，检查网络代理设置。CosyVoice 下载脚本支持 HuggingFace 回退，可以设置 HF_ENDPOINT=https://hf-mirror.com 使用镜像站。
